# c03 — change-001 步骤 2+3：community + joint-v2 接入，到「可以对战」

日期：2026-06-29　承接：c02（步骤0+1 MJAI 方言对齐）

## 目标
完成 spec 步骤 2（community 适配器）+ 步骤 3（joint-v2 适配器）+ run_arena 骨架，达成用户里程碑「**可以对战**」= community 与 joint-v2 在 RiichiEnv 真实三方对战跑通。v8（步骤4，方式定为本地 fetch+py3.10 venv）、规模化循环赛（步骤5）顺延。

## 做了什么（按设计）
桥接层 = 原生 MJAI。每模型 = 一个 MJAI 子进程引擎，跑在自己 .so 匹配的 python（community/joint 都用 conda `mortal` py3.12）；父进程（run_arena）跑在 RiichiEnv `.venv`，两侧只经 stdin/stdout 传 MJAI JSON，互不 import。

**统一 runner 协议**（规避两个原生 bot 协议不一）：父→runner 一行 = 一个 JSON 数组（该座 `new_events()` 全部事件）；runner→父 一行 = 一条动作 JSON（去 meta）或 `{"type":"none"}`。方言改写集中在父进程侧，runner 纯透传。

## 产物（全部 arena3p/，不碰上游/Mortal3）
- `engines/mjai_runner.py`：子进程入口，`--model {community,joint} --seat S`。community 经 `_pkgs/community` symlink package 调 `model.load_model`；joint sys.path 插入 `Mortal3/mortal` 复刻 mortal.py 加载（权重写死绝对路径 `archive/mortal.final.pth`）。
- `engines/subprocess_engine.py`：父进程侧 send/recv + 就绪握手 + stderr 转发 + 按模型方言 + `select_action_from_mjai` + none→pass 兜底。
- `engines/base.py`、`engines/registry.py`（启动规格 + 每模型 dialect 标记 + 强制 `CUDA_VISIBLE_DEVICES=""` 统一 CPU）。
- `dialect.py`：按模型方言。`to_env`（nukidora→kita，两模型共用）；`to_model_standard`（joint，仅 kita→nukidora）；`to_model_community`（community，kita→nukidora + 按座数组 3→4 padding）。
- `run_arena.py`：`--players a,b,c --hanchan N --seed S`，env 循环驱动各座引擎，收 scores/ranks 按模型聚合 avg placement / rank 直方图。
- `setup_pkgs.sh`：幂等建 `engines/_pkgs/community` symlink package（model.py / libriichi.so→3.12 .so / mortal.pth），`.gitignore` 忽略 `_pkgs/`。

## 关键发现（步骤2 实测，修正 c02 的「仅 kita↔nukidora」结论）
1. **community 的 .so 是 4 人格式 mjai（第 4 座掩码），不是 3 元**：喂 3 元 `start_kyoku` 报 `invalid length 3, expected an array of length 4`。须把按座数组补到 4：`scores`+35000、`tehais`+13×"?"、`deltas`+0。actor/target 仍 0~2（社区 4 座引擎容忍 3 座轮转）。桥接照搬 Mortal3 `scripts/cross_validate_community_so.py`（17 步状态比对 PASS）的 4 座掩码约定；deltas（hora/ryukyoku）该脚本未覆盖，按 4 座格式推断补 0，community 自对战整局未崩予以验证。
2. **joint（我们 libriichi3p）是原生 3 元 + nukidora**（权威 `Mortal3/.claude/MJAI_SCHEMA_3P.md`：`scores:[i32;3]`/`tehais:[[Tile;13];3]`），与 RiichiEnv 3 元一致 → 隔离测试直接吃 3 元事件回合法 dahai，仅需 kita↔nukidora。
3. **方言按模型分**：community = 4 座 padding + kita↔nukidora；joint = 仅 kita↔nukidora。
4. `select_action_from_mjai({"type":"none"})` 在 Rust 侧（`mjai_select.rs:101-104`）显式映射 `ActionType::Pass` → 弃鸣不会被误判成 pon（已验证）。`"kita" if three_player => Kita`、`nukidora` 走 `_=>None`（印证须改写）。

## 验证（全部通过）
- community runner 隔离构建 bot：相对 import 经 symlink package 解析，打印 `ready`。
- joint runner 隔离吃 3 元事件 → 回 `{"type":"dahai","actor":0,"pai":"F",...}`。
- `run_arena --players community,community,community --hanchan 1`：scores=[61300,26300,17400]（和105000）ranks=[1,2,3]，整局无错 → **步骤2 DoD + 闭合步骤1 第二 DoD**。
- `run_arena --players joint,joint,joint --hanchan 1`：sum 105000，整局无错。
- **里程碑**：`run_arena --players joint,community,community --hanchan 2`：两半庄均产出合法 scores/ranks（含负分 tobi，和守恒）。
- 全程 stderr 核验（community×3）：**0 行 WARN/Traceback** → 零静默兜底，每个 bot 决策经 select_action_from_mjai 干净映射，模型在真实决策。

## 坑/备注
- conda `mortal` 实为 **py3.12**（非旧文档说的 3.10）；community 用 `libriichi-3.12-x86_64-unknown-linux-gnu.so`（v0.1.0 多平台 .so 齐全）。子进程隔离让「谁的 .so 配谁的 python」成为非问题。
- 固定座位下「1 joint + 2 community」的 avg_place 机械地都=2.00，**非真实强度**；强度对比须步骤5 座位轮转 + 大样本 CRN。
- community 走 v0.1.0（自带 model.py+权重+.so）；cross_validate 用的是 v0.1.1 .so（同引擎，4 座一致）。
